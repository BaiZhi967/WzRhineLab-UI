# WzUI 需求反馈与版本排期流程

> 2026-10-14。适用于所有消费项目和维护者自己的新场景。主线自主推进，反馈是规划输入，不是等待条件。统一使用 [需求模板](../planning/templates/component-demand.md)。

## 1. 目的与原则

将缺陷、组件缺口、交互增强、设计不一致、文档和工程支持请求，转换成有范围、有归属、有版本和验收证据的工作。

不是任何请求都立即插入当前版本，也不是只有外部项目提出请求才能新增能力。主线可依据库内参考应用和明确的个人使用目的自行立项；外部需求则经过同样的范围与质量判断。

一个真实页面足以提出需求，不要求两个消费项目。使用者不必先精确命名组件，也不必一次填完全部技术字段；Agent 应先读取已提供的上下文，只补充会影响判断的信息，不能反复询问已知答案。

## 2. 入口与唯一记录

默认用 GitHub Issue 提交，并按模板组织；也可将经讨论确认的需求保存到 `docs/roadmap/requests/`。该目录在首个真实记录产生时创建，不预填虚构消费项目或需求。

编号采用 `WZUI-REQ-YYYYMMDD-NNN`，同日序号需先检查已有记录。Issue 与仓内范围卡同时存在时指定一个为权威正文，另一个链接到它；不维护两份会漂移的状态。一个请求可以关联多个实现任务，但不得把无关工作塞进同一范围卡。

主线任务使用执行清单中的任务 ID。请求进入版本后，需求记录和版本计划必须双向链接，标明交付子集和未纳入部分。

## 3. 最少受理信息

必需信息：要完成的用户操作、当前与预期表现、所用包版本、问题发生页面或最小复现、影响范围与暂时替代方式。只有概念性新需求时，提供场景和目标，未知技术项由评估补充。

缺陷增加复现步骤、环境、日志／截图、发生频率和回归版本；不能仅用视觉截图推断交互正确。不得提交 API key、用户真实资料、私密文件或完整敏感日志；用脱敏数据保留复现必要结构。

组件需求增加必须状态、数据形态、交互动作、视口、键盘／触摸、异步与取消要求，以及本次不需要的增强。

## 4. 分类与归属

| 分类 | 判断 | 默认处理 |
| --- | --- | --- |
| Defect | 已发布行为违背文档或合同 | 复现、定位、修复版本评估 |
| Enhancement | 已有组件增加有限能力 | 最小 API 差异及兼容评估 |
| NewComponent | 已有能力无法合理组合 | 确定基础／模式／领域归属 |
| Recipe | 现有公开组件足够 | 交付组合示例，不扩大基础 API |
| Design／Accessibility | 视觉、键盘、焦点、输入或可达性问题 | 找公共根因，不能只补一个页面 |
| Docs／Tooling | 文档、打包、导出、starter、元数据问题 | 进入文档或工程任务 |
| ConsumerLocal | 绑定具体接口、账号、原生权限或业务规则 | 留在宿主；可拆通用子需求 |
| ArchitectureStudy | 新包、引擎、底座、格式或信任边界 | 先 ADR／实验，不承诺直接实现 |

完整领域前端可以进入 WzUI，但不能把领域 UI 与宿主执行绑在一起。判断标准不是“对所有人是否通用”，而是是否值得在维护者的长期项目中统一维护、是否有可清楚隔离的公共合同。

## 5. 优先级与排期决策

| 优先级 | 典型影响 | 默认行为 |
| --- | --- | --- |
| P0 | 严重安全、数据损坏或核心已发布能力不可用 | 先确认影响并止损，维护者可批准中断当前工作 |
| P1 | 明确阻断且无可接受替代 | 优先评估修复或有限增强，记录范围交换 |
| P2 | 有替代的增强或计划内能力 | 进入下一次版本范围评审 |
| P3 | 探索、装饰或缺少明确目的 | 候选／实验池，不自动打断主线 |

严重度不等于版本归属。高优先级的新引擎需求仍需架构评估；低频缺陷也不能因为只有一个用户而忽略数据风险。排序考虑影响、复用价值、依赖成熟度、实现与长期维护成本；不设伪精确评分作为硬门槛。

维护者批准版本排期、范围变化和发布；Agent 负责整理证据、提出建议、执行已授权工作，不能自动把每条反馈标成当前版本 Must。

## 6. 需求状态与流转

```text
Reported → NeedsInfo（信息不足时）→ Triaged → Backlog → Scheduled
Scheduled → Implementing → LibraryValidating → Released
```

Triaged 只表示已分类和评估；Backlog 表示认可价值但未承诺版本；Scheduled 必须有目标版本、范围、依赖、任务 ID 和验收条件。Implementing 需有实际分支和改动；LibraryValidating 需有实现，尚未满足全部门禁；Released 必须记录真实包版本和发布证据。

任一未发布状态可经说明转 Deferred、Rejected、Duplicate 或 ConsumerLocal。延期必须写原因与重新评估条件；重复请求链接权威记录；不静默删除。信息不足不会暂停其他主线任务。

库侧验证失败回到 Implementing 并保留失败证据。已发布内容有回归时，创建关联缺陷或重新打开问题记录，但不抹掉曾经发布的版本事实。

## 7. 消费状态是独立维度

| 消费状态 | 含义 |
| --- | --- |
| NotRequested | 尚未安排消费方验证 |
| Pending | 已交付版本，等待消费方自己的验证 |
| Verified | 消费方记录了实际版本、页面、环境与结果 |
| Failed | 验证失败，附证据，等待重新分类 |
| NotApplicable | 纯库内／文档任务，不需要消费方验证；说明理由 |

`Released + Pending` 是合法组合。它允许 WzUI 继续下一版本，不表示消费项目的问题已经解决。`Released + Failed` 需要判断是库缺陷、使用错误、未声明环境还是新能力缺口，再进入相应队列。

一个请求可记录多个消费结果，不能因其中一个通过就把其他全部写成通过。消费方验证没有完成，不撤销真实的库侧发布事实；存在已确认的库侧严重缺陷时也不能以此为由忽略修复。

## 8. 范围卡与可执行合同

进入 Scheduled 前必须确定：场景、归属、目标包或 recipe、允许修改、公开 API 差异、数据与异步状态所有者、必须状态、依赖闭包、键盘／焦点、响应式、减动、SSR、资源释放、测试、文档与非目标。

必须分成“本次交付”和“后续候选”。当前只需树节点展开和选择，不自动追加虚拟化、拖拽、树表和文件系统适配。一个小范围交付不能把整个后续阶段标成 Accepted。

新底座、新重依赖、许可证变化、公开包拆分或内容执行边界进入 ArchitectureStudy；先交付决策或实验结论，再安排稳定实现。

## 9. 加入版本的方式

**当前主线**：与已冻结范围一致时链接已有任务，补充测试与验收，不重复创建组件。

**维护修复**：已发布缺陷可进入受控 patch 工作包。修复不顺带放入无关新功能；若需要支持多个版本线，明确移植范围和验证，不能暗中维护所有历史版本。

**下一版本**：普通增强与新组件进入候选池，在版本立项时选择；已接受不等于立即开发。

**提前子集**：后续阶段中的小能力在依赖满足时可提前交付。记录来源阶段、完成子集、剩余范围与回填任务，避免下一阶段再次从零开发。

不为每个反馈停下整个主线，也不因某个子任务受外部资源影响而停止所有无依赖任务。

## 10. 冻结后的范围变更

新增 Must、扩大 API、引入依赖或改变支持范围时，维护者确认变更记录。记录请求编号、理由、新依赖、影响测试、被延期／替换任务、当前暂停点、恢复点和版本风险。

没有明确范围交换或容量判断，不允许把原本有限版本变成无限吸收需求的集合。取消或延期也必须回填版本表、任务状态和需求记录，不能只改其中一个。

## 11. 实施、验收与发布

依照根 AGENTS 和 [质量规则](quality-and-release.md) 实施；缺陷先建立可复现测试，公共行为变化补状态、键盘、主题、减动、SSR 和包消费验证。

库侧验收使用参考应用和公开产物独立完成。消费项目提供额外验证，但不能成为 WzUI 唯一的复现场地。不能靠某个宿主构建成功替代库侧 API 和样式隔离检查。

发布前回填实际实现提交、文档、检查命令、环境、已知限制、升级方式和版本。发出交付说明后将消费状态设为 Pending 或 NotApplicable，而不是自动 Verified。

## 12. 回报、失败与关闭

消费方回报至少包含安装版本、入口与样式、操作步骤、目标环境和结果。失败应附最小复现与已排除因素，避免只写“不好用”。

缺陷请求在库侧交付后是否关闭 Issue，由其声明的解决范围决定；尚未验证的消费结果必须继续可见。不能用关闭 Issue 的操作伪装成所有应用已通过，也不能以长期 Pending 无限阻塞下一个版本。

对于无法复现的请求，保留环境和所缺证据，以 NeedsInfo 或 Deferred 管理；不把“没有复现”写成“证明没有问题”。

## 13. 示例与禁止事项

示例仅说明流程，不是已存在请求：某资源页面需要网格多选，可先判断是否由 ResourceGrid 与 SelectionToolbar 覆盖；已有 API 足够则提供 recipe，缺失行为则创建有限增强；UI 发布后由该页面自行安装验证。

禁止直接拷贝修改公共组件形成私有分叉来绕过反馈；禁止要求消费方透露密钥才能受理；禁止把截图、概念图或竞争产品清单当完整合同；禁止未经评估修改公共默认行为；禁止自动为所有历史环境提供兼容承诺。
