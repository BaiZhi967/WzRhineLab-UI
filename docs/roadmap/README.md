# WzUI 后续开发总路线

> 规划基线：0.2.0；源码基线：`c6b2af64107c5e03f6302a7481f1f930ce7d8bf8`；更新日期：2026-10-14。本文提交供维护者合并审阅，新增能力均为 Planned，不表示已经实现、验收或发布。

## 1. 产品定位与成功标准

WzUI 是维护者个人长期使用的 React 前端基础平台。它延续原创科研机构／档案设计语言，统一设计基础、组件、页面模式、内容呈现、数据交互和工程实践。目标是覆盖个人后续 React 开发中值得共享的前端工作，而不是把所有业务源码合并到同一个仓库。

主要使用者是维护者本人及协助开发的 Agent。不以公共社区规模、组件数量、兼容所有技术栈或商业化为目标。公开 npm 包是复用与交付方式，不等于需要建设大众化组件生态。

成功表现为：新页面主要编写业务数据适配和组件组合；新应用能够使用验证过的工程起点；同一种体验问题只修复一份公共实现；可选能力不拖累基础页面；Agent 能依据当前版本的 API 和 recipes 工作。

个人使用不降低语义正确、键盘操作、中文输入、性能、视觉一致性与版本可控性的要求。单一维护者仍然会有多个不同升级节奏的应用。

## 2. 路线运行原则

**自主主线 + 需求反馈，而不是消费项目接入驱动的等待队列。**

主线由维护者根据已明确的个人使用场景安排，并通过库内参考应用独立验证。消费项目发现缺陷、缺失组件或新使用方式时，统一提交需求反馈；经过归属、依赖、最小范围与风险评估后进入候选池或目标版本。没有新增反馈时，WzUI 继续原版本任务。

需求提出、需求接受、进入版本、库侧发布、消费方验证是不同事实。不得把某个应用的验证排期列为整个 WzUI 新版本的前置条件，也不得把发布组件写成已解决所有消费方问题。

现有能力继续维护；新增能力优先增量交付。不为目录整齐而重组正在使用的公开 API，不复制成熟引擎的通用机制，不把宿主查询、凭据、文件系统权限或运行时装入 UI 包。

## 4. 能力分层

| 层 | 长期内容 | 交付方式 |
| --- | --- | --- |
| 设计基础 | tokens、主题、排版、图标、动效、密度、响应式规则 | 现有 tokens 与设计规范 |
| 基础组件 | 表单、导航、浮层、反馈、布局原语、基础数据控件 | 现有 React 包 |
| 页面模式 | 集合浏览、主从详情、设置页、资源检查、阅读布局 | 拟议 patterns 包与 recipes |
| 领域前端 | 智能体界面、内容预览、分析视图、编辑与创作 | 已有领域包或按实际依赖拆出的可选包 |
| 应用前端支持 | 命令、快捷键、UI 状态恢复、错误边界、路由接入约定 | 薄适配与工程模板，不新造通用应用运行时 |
| 开发体系 | starter、API 索引、组件选择规则、测试工具、升级检查 | 参考应用、文档、脚本与 Agent 工作约束 |

现有五包继续存在。新包名称、目录与入口只是规划，真正创建前必须确认依赖图、包体预算、公开导出、样式入口和安装验证；不预建空包。

## 6. R1：页面与集合浏览

形成不依赖任何指定消费项目的完整路径：查找记录 → 筛选 → 切换视图 → 选择 → 执行操作 → 打开详情 → 章节定位 → 返回列表。

复用已有 Workbench、DataTable、Tree、表单与覆盖层。拟新增 ListDetail、InspectorPanel、QueryToolbar、AppliedFilters、ViewSwitcher、SelectionToolbar、ResourceGrid、RecordDetail、SectionIndex；纯排版使用页面 recipes，不机械包装成公共组件。

参考应用扩展现有 archive-desk，用档案和资源两类不同数据形态验证同一公共契约。示例数据明确标注；操作、焦点、异步状态与本地存储真实执行。它是库侧证据，不冒充生产后端接入。

前置条件为现有 0.2.0 公开能力及 R1 范围确认。无需等待消费项目。详细合同、任务和门禁见 [0.3.0 计划](0.3.0-plan.md)。

## 7. R2：内容阅读与预览

**目标**：让资料、文章和生成内容的阅读体验统一，不提前把预览做成完整编辑器。

范围包含正文排版与阅读宽度、标题锚点与目录、代码块、引用与来源、图片缩放与错误状态、附件与预览工具栏。先支持明确的文本、Markdown、代码与图片；音视频、PDF 或其他格式单独评估包体、Worker、许可证与加载方式。

新增公共渲染层时评估现有领域包中的代码、差异和文件展示能否复用。只有确有非领域消费者时才提取底层，保留必要兼容导出，禁止不带迁移说明的搬家。

依赖 R1 的详情与布局模式，但安全渲染评估可以独立进行。首轮交付阅读工作台 recipe：同一内容可在独立阅读页与侧栏预览中使用。

**退出证据**：长中文和长代码不破坏布局；目录定位可靠；链接协议受控；默认不执行内容中的脚本；不可信 HTML 按明确策略拒绝或净化；远程资源与本地资源访问由宿主授权；对象 URL 和 Worker 有释放路径；SSR 与懒加载边界有测试。

**不包含**：协同编辑、知识库后端、爬取、索引服务、完整办公文档引擎。失败的渲染适配可以独立延期，不回退已经通过的正文基础。

## 8. R3：数据分析与科研展示

**目标**：在集合浏览之上建立指标、证据与对比工作区，而不是仅加入图表外观。

候选范围为列显示配置、筛选摘要、受控数据视图、MetricPanel、EvidencePanel、RunComparison、ExperimentTimeline 和可选图表适配。先用明确的数据形态设计，不一次实现完整 DataGrid。

交付一个分析工作台 recipe：选择两组记录，查看指标差异，沿证据引用展开详情。缺失值、未执行、失败、过期值必须与真实的零值区分；单位、比较方向、分母和统计口径由调用者提供或明确声明。

图表引擎通过独立 ADR 选择，记录原生语义替代、键盘、减动、主题映射、许可证和体积。没有测量证据时不承诺十万行或任意实时频率；有性能问题才评估虚拟化。

**退出证据**：排序、筛选与数据源一致；批量选择范围清楚；比较结果可追溯；图表提供文本或表格替代；不同尺寸与数据密度有基准。没有后端数据时显示带说明的演示数据，不生成假实时读数。

**不包含**：服务端分析计算、评测执行、数据库查询语言、装饰型 3D 仪表盘。

## 9. R4：编辑与创作交互

**目标**：统一编辑入口、工具栏和状态表达，不从零实现完整编辑引擎。

先确定纯文本／Markdown／富文本中最需要的一条路径，以可选适配方式接入成熟机制。首轮只覆盖格式集合、中文 IME、光标与选区、撤销重做、粘贴、只读、错误、草稿与保存反馈。

保存由宿主执行，UI 不能把输入变化直接标成保存成功。明确 dirty、saving、saved、error、conflict 状态及对应操作；离开保护、失败重试、格式转换和撤销历史必须保持数据可恢复。

参考应用提供一份本地内容从编辑到预览再返回编辑的完整流程，覆盖失败保存、重载恢复与长文档；外部内容经过与 R2 一致的信任边界。

**退出证据**：目标格式往返不静默丢失数据；组合输入不会误触快捷键；撤销行为可预测；异常恢复可重复；未加载编辑器的普通页面不承担其主要依赖。

**不包含**：多人协同、云端文档服务、插件市场、完整视频剪辑或桌面办公套件。节点图、看板等复杂编辑能力只作为单独需求进入 R6 评估。

## 10. R5：工程体系与应用前端支持

该阶段做规模化固化，不是工具工作的起点。R1 开始就提供正确的 imports、Provider、样式顺序、组件选择说明和可执行 recipes。

长期交付包括：一个主力 Web starter；按真实需要补充 SSR 或桌面前端入口；页面 recipes 与安装验证；组件／状态／依赖／禁用方式元数据；升级与弃用检查；命令和快捷键规则；可注入存储的 UI 偏好恢复。

命令系统区分焦点作用域、输入区、中文组合输入、冲突和用户取消。偏好存储只保存 UI 配置，要求 namespace、schemaVersion、无存储降级、坏数据恢复和重置；不得把会话凭据或权限真实性放进去。

**退出证据**：从干净目录创建应用并构建；示例只使用公开入口或真实打包产物；无源码别名绕过导出；API 元数据与版本一致；模板依赖不夹带重型可选包；升级有可重复检查。

**不包含**：强制采用一种全局 Store、重造路由和请求框架、公共市场、无需求的全栈平台。CLI 只有在手工步骤稳定且重复成本可测时才立项。

## 11. 贯穿全程的视觉与质量工作

共享一个原创视觉语言，按工作台、阅读、展示三类用途调整密度、留白与装饰强度；这不是三套独立设计系统。高频业务不默认运行装饰循环；普通网站不强制变成高密度控制台。

通用图标沿已确认的基础层策略使用，定制图标仅承担确实缺失的语义；保持线宽、大小与视觉居中，不重启完整自绘通用图库。已有批准资产不由概念图自动替换。

每版都提供正确的状态矩阵、键盘与焦点、长文本、五宽度、主题／密度、减动、SSR、样式隔离、API、文档和安装验证。人工验证与自动化证据分开记录；范围与环境以 [质量与发布](quality-and-release.md) 为准。

## 12. 需求与版本的连接

缺陷和增强先建立需求记录。普通新需求在下一次范围评审中排期；明确的阻断缺陷可进入维护修复。需求即使源于一个页面也可被接受，但不能跳过架构和质量判断。

版本冻结后新增工作必须说明替换掉什么、扩大了什么风险和如何恢复原任务。没有记录的临时插入不计入版本。提前交付后续阶段的子集时，回填原任务，避免重复实现。

发布状态只由 WzUI 可控制的证据决定。消费项目可在自己的节奏中验证与升级；失败反馈作为新证据重新分类，不把“已发布”自动等同于“消费方已验证”。

## 13. 历史里程碑映射与风险

| 原规划 | 新处理方式 |
| --- | --- |
| M0–M10、M9.5、M12 | 已有能力与历史验收，保留记录，不重新立项 |
| M11 Rendering Lab | 转 R6 按需实验，不阻塞 R1–R5 |
| M13 库侧交付 | 纳入 0.2.0 基线；剩余领域候选分别归 R1／R3 等阶段 |
| M13 消费验收 | 归具体需求的消费状态，不再作为 WzUI 总路线门禁 |
| M14 | 可访问性和实际环境验证贯穿每版；额外语言／RTL 按支持范围立项 |
| M15 | 已发布的 0.x 不重新做首次发布；后续按每版发布与质量规则 |
| M16 | recipes、starter 与开发元数据，基础工作前移，规模化归 R5 |
| M17 | 进入 R6 可选适配评估，不预建多引擎体系 |
| M18 | API、版本、依赖、性能与安全持续治理；社区运营低优先级 |

本次改变后续优先级，不改写历史未执行项为通过，不宣称历史里程碑全部整体关闭。

主要风险是组件过度包装、公共包膨胀、宿主状态渗入、需求插入失控和只验证静态截图。对应约束是 recipe 优先、可选依赖隔离、受控状态、版本范围冻结和独立可交互参考应用。

## 14. 开工与交付

下一工作包从 [执行清单](execution-backlog.md) 的 P030-00 开始。先冻结公共契约，再实现依赖其上的组件。每个任务留下代码／文档路径、检查命令、结果、未执行项和剩余风险。

在 `.worktree/` 下创建隔离 worktree；中文小步提交；同一确认工作包最终汇总一个 PR，不按阶段提交多个 PR。未经授权不创建或触发自动 Actions；不要直接写入 main，也不要在规划 PR 中开始修改组件实现、依赖或版本号。
