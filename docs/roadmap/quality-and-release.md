# WzUI 质量、版本与发布规则

> 2026-10-14；适用后续全部版本。规划批准不等于实现通过；实现合并不等于已发布；已发布不等于所有消费方已验证。

## 1. 质量所有权

WzUI 为自己的公开 API、交互、设计规则、包产物和所声明环境负责。通过单元、交互、参考应用、真实安装与必要人工验证形成库侧证据，不依赖某一个消费项目完成全部验证。

消费项目为数据、业务权限、运行时、原生 API 和其真实使用环境负责。反馈会影响修复与规划，但消费方升级排期不是整个库的发布门禁。

已经确认的公共缺陷不能因为“消费方问题”而忽略。发布范围以本次实际证据为准；个人使用也不能把未执行的检查记作通过。

## 2. 版本验收层级

| 层级 | 证明什么 | 不能替代什么 |
| --- | --- | --- |
| 类型与单元 | Props、纯函数、状态转换和边界 | 浏览器行为与视觉 |
| 组件交互 | 键盘、焦点、异步、取消、实例隔离 | 完整页面操作 |
| 参考应用 | 公共组件在完整流程中的组合 | 真实后端或原生系统集成 |
| 打包安装 | dist、exports、types、CSS、依赖和实际消费 | 所有平台的运行验证 |
| 人工与目标环境 | 读屏、缩放、IME、触摸等真实体验 | 未运行的其他平台和设备 |
| 消费方回报 | 指定应用、版本和场景的结果 | 库全部 API 的完整正确性 |

## 3. 每个组件的完成定义

必须具备用途与非用途、API、状态矩阵、所有权与回调、键盘和焦点路径、长文本与布局、主题／密度、减动、异步失败／取消、资源释放、公开示例和必要测试。

已有组件变化还需说明默认行为、兼容性、原有测试和迁移影响。不能只增加 happy path；loading、empty、error、disabled、invalid、unknown 按该组件实际合同覆盖，不机械添加没有意义的状态。

只有包装排版而无独立行为的内容优先成为 recipe。每个 recipe 也必须可运行并说明数据适配点，不能是无法安装的展示片段。

## 4. 版本必需检查

下列为现有根脚本提供的入口，实施时核对实际 package.json。它们是待执行命令，不表示本文编写时已经运行：

```sh
pnpm check
pnpm test:e2e:all
pnpm test:examples:all
pnpm test:visual
pnpm release:check
```

`release:check` 不自动替代单独的浏览器、视觉和人工门禁。新增包必须进入 typecheck／test／build、API、license、包验证与 size 的覆盖范围，不能因为旧脚本只枚举已有包而漏验。

文档索引使用 `pnpm docs:index` 生成、`pnpm docs:check` 校验；API 使用对应脚本生成和核对。不得手写测试计数、手改生成 API 来制造通过，或用更新视觉基线消除未解释差异。

具体已有规则继续参考 [QUALITY-GATES](../development/QUALITY-GATES.md)、[安装说明](../development/INSTALL.md)、[发布流程](../development/RELEASING.md)。冲突时记录决策，不能静默削弱旧合同。

## 5. 响应式、输入与可访问性

新界面记录 320／390／768／1280／1920 宽度；嵌入模式额外验证容器宽度变化。长中文、英文长词、路径、空值、多行工具区与高密度数据不得导致不可操作溢出。

覆盖仅键盘操作、合理 focus 顺序、关闭与删除后的 fallback、中文组合输入、200% 缩放和 forced colors。读屏与触摸证据按该版本声明的目标环境逐项记录。

自动 axe 或浏览器模拟不能写成 NVDA、VoiceOver 或真机人工通过。已有环境证据也不能无限继承到发生交互变化的新版本。新的语言、RTL 或设备支持按明确需求立项，不因历史候选表出现过就自动成为所有版本的全量门禁。

对于本版声明范围内必须的人工验证，缺失时保持 Validating；对于未声明的新范围，明确列为未覆盖，不声称支持。历史未执行项仍保留，不由路线改写为成功。

## 6. 动效与视觉一致性

继续使用现有 tokens、Provider、图标基准与 motion/react。所有交互动画可中断，减动时有正确降级；动画不能延迟业务事实、禁用状态或读屏信息。

验证快速开关、反向切换、目标变化、隐藏页面、离开视口和卸载。展示型循环与真实状态分开；普通页面不因引入组件就自动启用扫描或轨道特效。

视觉差异逐项解释并由维护者确认。概念图是参考，不是实际像素、图标细节和虚假数值的权威。

## 7. 性能与资源基准

每个新增模块建立空载、典型与压力场景。记录数据数量、分页大小、内容长度、图片规格、视口、浏览器、设备、测量工具和运行次数；没有这些条件的数字不能作为发布证据。

0.3.0 使用拟定的 1,000 条档案／240 条资源数据集并明确分页。测量输入响应、切换、详情打开、DOM 规模、内存或资源释放、基础入口和可选模块包体。先建立实际基线，再由维护者批准预算，不把本计划中的数据规模写成已测性能。

基础入口不得新增不相关的重依赖。可选包需要检查构建产物、lazy chunk、首次加载和卸载，不能仅凭 tree-shaking 标签判断隔离正确。

## 8. SSR、样式隔离与真实产物

测试服务端首屏与 hydration；不在模块顶层读取窗口、存储或文件 API。多实例的主题、消息和状态相互隔离；Portal 保持作用域；不得污染宿主全局 CSS。

至少用打包后的真实产物在干净消费者中安装与构建，检查 imports、types、styles、peer 与依赖解析。不用工作区源码 alias 替代该门禁。

参考应用可作为库侧回归；原生系统、浏览器特性与不受支持的引擎必须分别记录。一个环境通过不能自动代表全部桌面系统或浏览器版本通过。

## 9. 发布与维护策略

当前 0.2.0 是发布基线。下一功能版本目标 0.3.0；后续版本号为候选，不在规划 PR 中修改 package.json 或执行发布。

项目约定：patch 用于已发布合同下的修复和不改变行为的文档调整；minor 用于确认范围的新能力。0.x 的不稳定语义不作为静默破坏兼容的理由，破坏变更必须单独说明并提供迁移路径。

默认遵循现有发布脚本的同步包组。无需求时不改成独立多版本发布；需要维护旧版本线时明确修复范围与停止条件，而不是承诺永久支持全部版本。

消费项目固定到已验证版本或明确兼容组，不追踪开发分支。预发布采用显式标识与分发策略，不覆盖稳定入口；版本、Git commit、发布产物和验收记录必须能对应。

## 10. 候选、发布与回滚步骤

确认范围和所有 Must 任务 → 在同一源码基线完成门禁 → 生成 changelog／升级说明／包产物 → 验证实际安装 → 形成一个汇总 PR → 按维护者授权发布 → 核对 registry 版本与安装 → 回填需求交付状态。

任何步骤未执行就记录未执行。不要直接运行指向旧版本号的 dry-run 命令；先按 RELEASING 核对目标版本与脚本。代码合并后仍须完成真实发布和安装检查。

回滚优先让消费方恢复上一已验证版本或兼容组；修复后发布新版本，不覆盖已发布 tarball。UI 偏好或内容格式变更若存在迁移，提供旧版本可恢复路径。严重问题按影响评估停止推荐有问题版本，并记录事实，不擅自删除版本。

## 11. 证据记录

每份验收记录包含：版本与 commit、工作树、环境与工具链、任务／需求 ID、实际命令、实际计数、日志路径、视觉差异、人工检查者与结果、未执行及原因、已知限制、发布状态和回滚说明。

状态区分 Planned、Implementing、Validating、Accepted、Released。Accepted 是定义范围的验收通过；Released 需要真实发布证据。消费验证使用独立字段，参见 [需求流程](demand-workflow.md)。

本轮是规划文档工作包：仅做文本、链接、状态、目录和改动范围检查，不声称已执行未来组件的测试或 npm 发布。

## 12. Actions 与交付约束

默认使用本地检查。未经授权不创建、手动触发、重试或变更 Actions；提交前读取现有 workflow 的事件与 paths，不能假设纯文档永远不触发工作流。

本次基线的 Pages 流水线仅在 main 上相关构建输入变化或手动触发时执行。后续规则可能变化，每次重新检查。保持该已批准流水线不变，也不以新路线为由额外开自动 CI。

文档 PR 与实现工作包分别交付；每个确认的工作包在 `.worktree/` 下工作、中文小步提交，最终一个 PR。质量不依赖 Actions 是否可用，不把没有运行的 CI 写成全绿。
