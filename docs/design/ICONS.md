## 1. 设计目标：建立一个图标家族，而不是一批相似图片

### 1.1 项目身份

WzRhineLab UI 的方向是原创的科研机构与档案工作台：暖白表面、深墨信息、清晰网格、少量研究橙，以及具有真实语义的仪器结构。它不是官方游戏 UI，不复制官方标志或图标，也不是霓虹科幻、军事瞄准 HUD 或拟物设备插画。依据为项目《设计总纲》与视觉规范。[^r-design]

图标需要完成四件事：用户能理解其操作或对象；混排时看起来来自同一套系统；在小尺寸和不同主题中保持稳定；后续新增时有明确的判断依据。

### 1.2 决策优先级

**语义与可访问性 > 可读性与视觉居中 > 家族一致性 > 复用与维护 > 个性装饰。**

当“更像科研机构”和“更容易认出关闭、搜索、下载”发生冲突时，保留通用操作的识别方式。不得为了品牌差异把关闭画成复杂机械装置，把设置画成无语义的机构徽记。

### 1.3 风格正向定义

- **精确**：同类圆环、支架、折角和分隔线共用尺度；重复细节对齐，交接干净。
- **克制**：每条线服务于识别，不用悬浮点、短划线或编号填补空白。
- **机构秩序**：正视图、稳定轴线、可复用几何；避免把对象随机倾斜以制造动感。
- **温和技术感**：整体轮廓利落，线帽与连接处柔和；不是粗圆卡通，也不是锋利尖刺。
- **视觉居中**：主体看起来位于图标槽位的中心；不是仅保证 SVG 标签或外接框居中。

### 1.4 明确不做的方向

不做多色渐变、玻璃高光、霓虹发光、3D 等距投影、重阴影、默认实心填充、贴纸式描边、卡通圆鼓造型；不把背景网格、刻度、准星和文字编号塞进每个小图标；不在同一界面混用不同图标库来“临时补齐”。

> 附记（2026-10-14 维护者决策，见[批次 2026-10-14-batch-02](icons/icon-review/2026-10-14-batch-02/scope.md)）：消费项目可以采用 Lucide 作为基础图标层；本库保持零运行时图标依赖，仅按本规范提供 Lucide 未覆盖的定制图标，宿主应将 Lucide 组件的 strokeWidth 统一为 1.75 以匹配本族线宽。上条禁止的是无规划的临时混用，不包括经此决策确立的"Lucide 基础层＋本库定制层"分层。规范下次修订时并入正文。

| 问题 | 权威与处理方式 |
| --- | --- |
| 项目整体气质、原创边界 | 已采用的 `DESIGN.md` 与设计 ADR |

现状违反规范时，应登记差异并修复，不把缺陷升级为新规则。规范与 API 有冲突时，先通过 ADR 和迁移决策解决，不在业务页面以 CSS 补丁绕过。

### 2.3 三种不同的“确定”

**方向确定**：认可暖白／深墨、单色线性、仪器与档案结构。  
**规格确定**：某枚图标的语义、几何与校准已审核。  
**发布确定**：实现、目标尺寸、目标平台、可访问性和包导出已验证。

三者不能互相替代。上一轮参考板属于第一层和第二层的候选输入，尚不是第三层。

## 3. 图标分类：共享语言，不共享所有装饰

| 类别 | 职责 | 允许的辨识手法 | 禁止事项 |
| --- | --- | --- | --- |
| Foundation／通用操作 | 搜索、关闭、确认、方向、播放、暂停 | 清晰轮廓、标准操作符号、最少结构 | 为了科研感额外增加圆环、切角框和短线 |
| Archive／档案对象 | 文件、目录、集合、标签、归档、权限 | 折页、页签、抽屉分隔、简化装订结构 | 给每个对象画多层边框或虚构编号 |
| Research／研究仪器 | 实验、观察、扫描、光学、信号、分层 | 对称支架、同心结构、扫描括角、简化仪器剖面 | 写实机械零件、密集刻度、无语义卫星或轨道 |
| Workspace／工作空间 | 终端、会话、面板、组件入口 | 统一屏幕比例、命令符、布局分区 | 给所有图标增加一个窗口外框 |
| Status／状态 | 警告、成功、错误、加载 | 标准状态符号、必要文字与容器状态 | 只用颜色区分状态；把装饰灯当真实状态 |
| Ornament／装饰图形 | 展示页上的轨道、标尺、准星 | 在有解释的展示空间中使用 | 注册为普通操作图标，或挤占实际点击区域 |

分类只决定语义与构造词汇，不意味着 Research 可以更粗、Archive 可以更方、Workspace 可以另用一套圆角。分类徽记、空状态插画、产品 Logo 不属于本图标规范的默认小尺寸集合。

## 4. 家族不变量：后续开发不得自由改动的部分

| 编号 | 必须保持的规则 | 允许变化的部分 |
| --- | --- | --- |
| F01 | 母版 `viewBox="0 0 24 24"` | 展示尺寸；经评审的小尺寸优化几何 |
| F02 | 默认线宽 `1.75` 个母版单位 | 不通过消费端逐枚改线宽调重量 |
| F03 | `stroke-linecap="round"`、`stroke-linejoin="round"` | 图形本身的直角、斜角和曲线 |
| F04 | 默认单色、`fill="none"`、`stroke="currentColor"` | 已记录的微小实心语义点；不发展双配色默认集 |
| F05 | 独立透明字形，没有内置底板、标签或外部装饰 | 按钮与导航等容器自行绘制背景和状态 |
| F06 | 字形在统一槽位中视觉居中 | 经评审的矢量内部光学补偿 |
| F07 | 同类结构共享比例、方向和内部间距 | 不同语义必要的轮廓差异 |
| F08 | 新图标进入同一公共体系与验收流程 | 通过 ADR 决定的兼容迁移，不绕过为业务私建图库 |

“更小就随手加粗”“选中就变实心”“深色模式单独放大”“这页偏一像素就加 margin”均不是允许变化。

## 5. 母版网格、边界与基本形状

### 5.1 统一计量

本文用 **u** 表示 `24 × 24` 母版中的 SVG 用户单位，用 **CSS px** 表示实际布局尺寸。两者只在 24 CSS px 等比展示时数值相同。所有补偿量和几何门槛必须注明单位。

原点在左上；基准中心为 `(12, 12)`。主体首先围绕中轴构造，再处理折页、柄部等非对称部分。

### 5.2 区分三种边界

**视口边界**是 `[0,24] × [0,24]`；**路径边界**是中心线或填充几何覆盖的范围；**可见笔画边界**还包含线宽、圆头与连接。评审留白必须使用第三种，而不是只看路径坐标。SVG 的描边与线帽会扩展几何外观。[^w-svg-paint]

采用以下项目门槛：主体的可见笔画应优先位于 `[2,22] × [2,22]`；常规正式字形不得超出 `[1.5,22.5] × [1.5,22.5]`。这是最大可用区域，**不是每一枚都要填满的方框**。较小的确认、关闭、箭头不得为了填满而拉长。

特殊语义确实需要越过 1.5u 留白时，必须取得字形级例外并记录理由；禁止通过改变 viewBox、隐藏溢出或缩小整张参考板掩盖问题。当前草案 `network` 的已有统计需要按此新门槛重新处理，不能自动获得例外。

### 5.3 形状起始 keyline

下表是**路径中心线的绘制起点**，不是统一外接框要求。完成后仍按实际笔画、重量和视觉中心调整。

| 形状 | 起始几何 | 设计意图 |
| --- | --- | --- |
| 正方形外轮廓 | 左上 `(4,4)`，右下 `(20,20)` | 为密实轮廓留出呼吸，不画成按钮边框 |
| 圆形 | 圆心 `(12,12)`，半径 `8.5u` | 与方形混排时用略大的轮廓补偿圆形的视觉面积 |
| 横向框 | 左上 `(2.75,5)`，右下 `(21.25,19)` | 终端、文件夹等横向对象的起点 |
| 纵向框 | 左上 `(5,2.75)`，右下 `(19,21.25)` | 文档、容器等纵向对象的起点 |
| 菱形／斜向主体 | 先围绕 `(12,12)` 构建，再约束笔画边界 | 不把旋转后的图形裁切或挤满视口 |

圆形尺寸和其他起点是本项目提案，不要求存量草案无差别缩放到这些坐标。相同语义家族一旦批准具体比例，后续派生图形应沿用该比例。

### 5.4 坐标与角度

新绘制的轴线和重复细节应优先落在 `0.25u` 的设计步进上；优先使用水平、垂直与 45° 斜线。圆弧、真实语义需要的三角形和仪器倾角不受“所有斜线都必须 45°”的错误限制。

复杂曲线控制点和最终光学补偿可使用更细坐标，通常保留不超过三位小数。不要为了小数整齐破坏曲线或已有的视觉校准。1.75u 描边并不能在所有尺寸与缩放倍率下同时对齐设备像素，因此禁止宣称“全部使用整数坐标即可消除模糊”。

## 6. 线条、转角、间隙与视觉重量

### 6.1 线宽只建立一条基线

默认描边是 `1.75u`，不在同一集合中混入 1、1.5、2 或 2.5u。细节太多时先删细节，不通过缩细整枚图标解决；显得太轻时先检查轮廓尺度与结构，不通过局部加粗解决。

不得让外轮廓一套线宽、内部细节另一套线宽。单一语义点如信息点可用小实心圆，但必须在字形规格中登记，且采用 `currentColor`。

### 6.2 圆头不等于整体圆润

线帽与连接的 round 是笔画收尾规则；对象仍可以有直立边、45° 切角和规整折页。不得把所有外轮廓改成大圆角矩形，也不得为了“工业感”换成尖锐 miter 连接。

同类小矩形的路径圆角优先从 `1–1.5u` 选取；直角路径已经有圆角连接时，不再叠加很大的几何圆角。档案／仪器外框的切角优先从 `2u` 起步；同族派生图标不得各用一个切角尺寸。功能性折页与装饰性切角是两种结构，不能随意互换。

### 6.3 细节间隙

彼此独立、需要区分的笔画，其**描边后的净间隙**在母版中应不小于 `1.5u`；供 14px 使用的必要细节应优先达到 `1.75u`，否则简化或限制最小尺寸。平行的 1.75u 线条要获得 1.5u 净间隙，中心线间距至少为 3.25u。

以上不用于图形本来就应相接的连接点。必须避免“本该分开却恰好相切”的模糊关系：要么明确相接，要么明确留白。禁止用背景色填充掩盖相交线；需要空心节点时应裁短底层线段，使深色主题仍成立。

### 6.4 控制结构复杂度

每枚字形只表达一个主要对象或操作。优先保留主体轮廓和一至两组识别细节；超过八个独立可见结构时进入复杂度复审，但不把 SVG 元素数量作为机械合格线。把所有线合并成一个 `path` 并没有减少视觉复杂度。

科研图标也必须能回答“删掉这一条线会损失什么语义”。无明确答案的微小刻度、悬浮短线和圆点应删除。复杂状态叠加优先交给相邻文字、Badge 或容器，不默认在 16px 图标上叠多个角标。

### 6.5 视觉重量校准

用正式基准中的稀疏、密实、圆形、方形和非对称图标混排比较；不能只把所有图标做成相同宽高或相同墨量。等面积不意味着等视觉重量。

密集图标优先减少重叠与内部线条，再调整轮廓；稀疏图标保持其语义需要的留白。不得为补足墨量给关闭或箭头加一个外圈。

## 7. 家族造型规则与可复制的设计决策

### 7.1 文件与档案

普通文档默认正视图、一个折页、至多两条内容横线；同族折页位置与宽度一致。代码文件、加密文件、研究记录从同一文档母体派生，不能每次重画一张比例不同的纸。

文件夹保留清楚的页签和横向容器；Folder 与 FolderOpen 表达不同状态，不可为了重用现有名称把关闭文件夹冒充打开文件夹。档案柜采用一组明确的抽屉分隔和一致把手，不能为增加细节扩展到多排柜体。

### 7.2 光学、扫描与研究设备

光学核心围绕中轴组织圆环与支架；左右支架必须同高，横向接点必须对应。扫描括角共享长度与角度，不能每个角大小不同。

显微镜只保留目镜／镜筒、支撑与底座等识别结构，不画多级机械关节。样本容器的内部样本与外框共享中心；不把样本替换成无语义的宝石装饰。

轨道、卫星和波形仅用于真正对应的任务。网络节点表示连接关系，不能被用作任意“AI”标志。不得将某一仪器轮廓直接宣布为产品 Logo。

### 7.3 终端、面板与对话

终端保留简化提示符与光标，不添加可读命令字符串；屏幕、面板类共享基本框比例。对话尾部应清楚但不夸张，不靠移动整个气泡容器弥补尾部造成的视觉偏移。

### 7.4 基础操作与状态

关闭由两条等重的斜线组成，交点是结构基准；确认使用开放勾形，不增加包围框。箭头和 chevron 分别维护，不用缩短箭杆制造一枚临时 chevron。

播放／运行采用稳定的三角轮廓；暂停采用两条一致竖向结构。成对状态必须在同一按钮中比较，不能单看每枚居中就认为切换时不会跳动。成功、错误、警告沿用明确语义符号，不通过随机改变轮廓来显得原创。

## 8. 光学居中：核心设计与验收机制

### 8.1 需要同时处理的三个层面

**布局居中**：SVG 的固定尺寸槽位位于按钮、行或导航项规定的位置。  
**几何归一化**：合理的主体尺度与可见笔画边界围绕设计坐标组织。  
**光学校准**：综合主体、重心、柄部、折角、方向感和留白，使实际观看时没有明显偏移。

`display:flex; align-items:center; justify-content:center` 只能处理第一层。外接框中心、alpha 墨量重心都可以提供测量，但均不能单独证明第三层合格。

### 8.2 校准必须分两步记录

第一步是**几何归一化**：修正原稿的尺度或起始坐标；优先重写母版坐标，不把所有源图偏差积累成一个巨大 transform。第二步是**光学微调**：在归一化后的字形上做小幅比较。

规格记录必须把 `geometryNormalization` 与 `opticalCorrection` 分开。参考包中的 `translation` 混合了外接框归中和墨量辅助结果，不能直接解释为最终光学偏移，也不能一律复制到 React 包装器。

光学微调应从 `0u`、`±0.125u`、`±0.25u`、`±0.5u` 的候选开始比较。任一轴超过 `0.5u` 时必须复审原因；超过 `1u` 时原则上先重构主体几何，再谈微调。上述是审查触发值，不是让算法将偏移量直接钳制到阈值，也不适用于尚未归一化的旧稿总平移量。

### 8.3 标准操作流程

1. 在统一母版中绘制，先检查必要对称轴、重复结构与笔画边界。
2. 输出无文字、无底板的字形，同时记录含描边的 bbox；可附 alpha 重心作为诊断数据。
3. 先进行几何归一化，再并排输出零微调与两个邻近候选；禁止直接套用“搜索都偏左”“播放都偏右”的统一经验值。
4. 在 16／20／24 CSS px、相同槽位和同族邻居中比较；必要时补 14／18px。
5. 在按钮、单行列表、导航、输入框及状态切换中复核；同时去掉辅助线再看。
6. 由维护者确认选用版本，记录理由、参数、截图和复核环境。AI 的视觉意见可以辅助，不能自填维护者批准。

### 8.4 不同形状的重点

| 类型 | 校准要点 | 常见错误 |
| --- | --- | --- |
| 圆、对称扫描框、关闭 | 中轴、等距、上下左右笔画一致 | 对本来对称的图形加无理由偏移 |
| 搜索 | 圆形主体与斜柄形成一个整体；观察右下拖拽感 | 只居中圆圈，或只对齐带柄的 bbox |
| 播放／运行 | 轮廓三角形的方向感与按钮中的视觉位置 | 把实心三角形的重心算法用于空心轮廓 |
| 文件夹 | 文件夹主体与顶部页签共同平衡 | 忽略页签，或让页签把整体拖到一边 |
| 显微镜、卫星 | 主体、支架、斜向轮廓是否失衡 | 按最远的细小突出点缩小整枚图标 |
| 下载、上传 | 托盘是否保持共用基线，成对切换是否跳动 | 独立居中后托盘上下位置不一致 |
| 分栏、会话 | 主框的稳定性与内部非对称分区 | 为了内部墨量居中把外框明显推离中心 |

### 8.5 存放位置与责任归属

字形自身的补偿必须固化在正式矢量几何或库内的单层平移组中，二者只能选一个实际生效的位置；规格记录保留历史值。禁止母版和包装器各执行一次相同偏移。归一化涉及缩放时，应调整或烘焙路径几何，并确认实际描边仍是1.75u；不得保留会顺带改变线宽的任意scale／skew组作为对齐补丁。

消费端不得通过 `margin-left`、`top`、`translateX` 等按图标名修补光学位置。整行所有图标一起偏移时优先修容器；仅一枚在所有容器都偏时修字形；同一枚只在某个组件偏时修该组件布局。

### 8.6 验收定义

不以“重心误差小于某个浮点阈值”替代视觉验收。合格需要：结构轴线无无意偏差；同组混排没有明显突出或下坠；按钮边缘留白感平衡；相反方向和成对状态切换不跳位；去掉校准线后仍成立。需记录 100% 原尺寸观察，不只看放大参考图。

## 9. 尺寸、描边缩放与小尺寸策略

### 9.1 母版与展示尺寸分开

正式字形仍以 24u 母版为唯一默认坐标体系，主要验收 16／20／24 CSS px；实际出现 18px 时增加该尺寸。当前 token 中 `--rl-icon-size-sm/md/lg` 分别是 **14／16／20px**，不可在本轮文档中重定义成 16／20／24，也不可偷偷改变公共 token。[^r-tokens]

| 展示尺寸 | 使用定位 | 本规范要求 |
| --- | --- | --- |
| 14px | 存量紧凑控件、简单辅助符号 | 只对实际使用的字形声明支持；复杂科研图标不得未经验证直接缩放 |
| 16px | 表格、菜单、紧凑按钮 | 基础验收尺寸；不依赖微小刻度识别 |
| 18px | 已采用此尺寸的导航或控件 | 作为实际消费尺寸专项检查，不另建18u图库 |
| 20px | 主导航、常用操作按钮 | 主要推荐使用尺寸之一 |
| 24px | 较宽松工具区、展示与基础母版核对 | 不意味着图形必须铺满24px |
| 大于24px | 文档放大预览、特定大按钮 | 可等比展示；不能据此推导小尺寸质量 |

### 9.2 不默认使用 non-scaling-stroke

遵循当前包装器的等比缩放路径，默认不启用 `vector-effect="non-scaling-stroke"`。该属性会改变缩放时的描边行为，不能把它视为“更清晰”的通用开关。[^w-svg-coords]

1.75u 线宽等比展示时的布局厚度约为：14px → 1.021px；16px → 1.167px；18px → 1.313px；20px → 1.458px；24px → 1.75px。这是 `1.75 × 展示尺寸 ÷ 24` 的几何结果，不是跨平台像素外观保证。

### 9.3 先简化，后分尺寸母版

同一字形应先尝试在全部目标尺寸成立。若 14／16px 必要细节粘连，优先简化内部结构，或将它的最小支持尺寸设为20px，并使用经过验证的更简单替代符号配合文字。

只有单母版方案无法兼顾语义时，才允许尺寸优化几何；优化稿仍用24u坐标，保留同一语义与家族特征，并在规格中登记 `supportedSizes`。当前包装器没有已核实的自动尺寸变体选择能力，加入这项能力须独立实现与测试，不能先在文档示例中假装存在。

## 10. 色彩与主题：单色默认，信号色有语义

### 10.1 颜色归属

字形内部只描述结构；颜色由宿主 `color` 和语义 token 传入。禁止 SVG 内硬编码暖白、深墨、研究橙或白色遮挡块。以下数值只用于阅读当前基线；实现必须引用 token。[^r-tokens]

| 角色 | token | 浅色值 | 深色值 |
| --- | --- | --- | --- |
| 默认图标 | `--rl-fg-primary` | `#20251F` | `#E6E9E2` |
| 次要图标 | `--rl-fg-muted` | `#505850` | `#AEB8B6` |
| 明确的品牌强调前景 | `--rl-accent-text` | `#A8421B` | `#FFB07A` |
| 强调背景／信号填充 | `--rl-accent` | `#E56A32` | `#E9874F` |
| 强调底上的图标 | `--rl-fg-on-accent` | `#20251F` | `#11181B` |
| 反相底上的图标 | `--rl-fg-inverse` | `#F7F6F1` | `#11181B` |
| 禁用图标 | `--rl-fg-disabled` | `#80857C` | `#75858A` |
| 焦点环 | `--rl-focus` | `#1F5AA8` | `#8DB8F2` |

### 10.2 强调色不属于某一类图标

Research 图标不能默认全橙，Archive 不能默认全灰；同一语义在默认、选中、危险或禁用状态中按组件 token 改变颜色。浅底强调图标优先选前景角色 `--rl-accent-text`，不能仅因为参考板上有橙色，就直接使用亮橙填充角色。

颜色不得成为唯一信息通道。选中状态应同时有容器标记、背景、文字或合适的可访问状态；焦点环与选中样式必须可以同时被辨认。

### 10.3 对比度与细线可读性

需要识别控件或理解内容的图形，按 WCAG 2.2 SC 1.4.11 检查与相邻颜色至少3:1；纯装饰与不可用控件有相应例外，不能将例外套到正常可操作控件。对比度使用实际计算颜色与有效叠加背景，不能以抗锯齿边缘像素代替规范计算；同时另做原尺寸细线可读性检查。[^w-contrast]

深色主题不得默认另加粗0.25u、另缩放105%或改成描边发光。确有跨主题重量问题时，先检查颜色与密度，再评审家族级方案。

## 11. 状态与动效：改变状态，不破坏字形

| 状态 | 允许的处理 | 不允许的处理 |
| --- | --- | --- |
| default | 使用宿主前景与固定槽位 | 无状态地全部使用橙色 |
| hover | 宿主前景、边框或背景反馈 | 随意加粗图标、弹跳或放大 |
| pressed | 沿用组件动效与按压反馈 | 为某一枚另写位移，覆盖光学补偿 |
| selected | 语义色与容器标记组合 | 默默从线性集切换为实心集 |
| focus-visible | 宿主可见焦点环 | 只改变图标颜色；用品牌橙代替所有焦点色 |
| disabled | 不可用语义与禁用token | 只把透明度调低，却仍能触发操作 |
| loading | 保持槽位与可访问状态，使用批准的加载符号 | 让任何图标都随意旋转；制造无限装饰扫描 |
| success／warning／error | 标准符号、文本、语义token | 仅以颜色或灯点表达结果 |

动效复用项目 Motion 规范与 `--rl-motion-*`，不在每枚 SVG 内嵌 SMIL、独立CSS关键帧或永久运行的计时器。减少动态效果时必须仍可理解状态。

折叠箭头可以随状态旋转，但旋转以已校准的固定槽位中心为基准；对齐平移与状态旋转要分层，防止后者覆盖前者。旋转、切换和淡入淡出不得引发文字位移或按钮宽度变化。本站不把图标描边逐笔出现作为默认交互。

## 12. 布局、文本与点击区域

### 12.1 槽位规则

同一组列表、菜单或导航使用相同尺寸的图标槽位；SVG 应禁止 flex 收缩。图标不能因为旁边文字更长而变窄。单行内容按该行视觉中心对齐；多行条目明确选择“对齐首行”或“对齐整块”，相同组件中不得混用。

图标与文字间距优先复用 `--rl-control-gap`：当前舒适密度8px、紧凑密度4px。具体布局遵从组件密度，不在字形内部加透明边距。正文内联符号的行内对齐由专用排版规则处理，不通过给所有 `.rl-icon` 加一个全局 `top` 值解决。[^r-tokens]

### 12.2 图形尺寸不等于目标尺寸

桌面常用 IconButton 的点击区域应优先32／40px；触控场景优先48px，与现有控制尺寸体系协调。当前紧凑控件存在28px高度，并不意味着所有图标按钮必须重写成40px；需要按实际目标面积与周边间距验收。[^r-tokens]

WCAG 2.2 AA SC 2.5.8 的目标尺寸要求是至少24×24 CSS px，存在间距、等效控件、行内、用户代理控制和必要性例外；44×44对应更严格的增强目标尺寸准则（AAA），不能把44px写成AA统一最低值。项目选择48px触控目标，是项目体验标准。[^w-target-min][^w-target-enhanced]

点击区域必须由真实控件承担，不让用户精准点击SVG线条。不得把图标四周看似空白但实际不可点击的区域描述为扩大了目标。

### 12.3 跨平台与缩放

必须区分 CSS 像素、设备像素比、操作系统缩放和浏览器缩放。Windows 常用缩放与 macOS Retina 至少有实际平台抽样；Linux截图或浏览器仿真不能冒充真实Windows/macOS结果。

基础检查包括16／20／24px在DPR1和DPR2的渲染；实际支持的14／18px追加检查；平台验收记录100%与125%／150%等实际缩放。不同环境分别维护截图预期，不能要求不同浏览器抗锯齿逐像素完全一致。

## 13. 可访问性与方向性

### 13.1 三种使用方式

**纯装饰**：图标旁已有同义文字，字形对辅助技术隐藏，避免重复朗读。  
**独立传意**：没有同义可见文字时，提供准确的可访问名称。  
**可操作控件**：按钮／链接承载操作、键盘语义与名称，SVG通常作为其装饰子元素。

当前 `Icon` 在提供 `aria-label` 时输出 `role="img"`，否则默认 `aria-hidden`；它根据 `aria-label` 而不是 `aria-labelledby` 选择分支。不得把“SVGAttributes类型接收某属性”误认为包装器的可访问行为已支持所有组合。支持 `aria-labelledby` 或显式装饰模式时需另补设计与测试。[^r-wrapper]

现有API使用示意，均使用已核实的公共名称：

```tsx
import { Icon } from '@wzrhine/react/icons';

// 名称属于按钮，内部图标保持默认的装饰模式。
<button type="button" aria-label="打开设置">
  <Icon name="Settings" size={20} />
</button>

// 有同义可见文字，不再给图标追加相同 aria-label。
<span><Icon name="Check" size={16} /> 已完成</span>

// 图标需要独立传达信息时提供准确名称。
<Icon name="ShieldAlert" size={20} aria-label="存在安全风险" />
```

此处只演示图标语义；实际产品应使用项目已建立的Button／IconButton及样式，不把无样式示例当成完整交互实现。

### 13.2 方向策略

规格必须记录图标是**物理方向**、**阅读顺序相关方向**还是**非方向对象**。明确名为ArrowRight的图形表达物理向右，不能在所有RTL场景中静默改变为向左。逻辑“下一步／返回”由组件根据语言方向映射到正确的方向图标。

展开／收起、前进／后退按真实交互语义确定；播放三角、放大镜、文件折页、实验瓶、时钟、品牌标志不因RTL整体镜像。传输上下方向不得因左右阅读方向改变。镜像后仍需检查非对称字形的光学位置，禁止对整套图库统一 `scaleX(-1)`。

## 14. 命名、语义与图标登记

### 14.1 名称规则

源资产文件名使用 kebab-case，公共 `IconName` 延续现有PascalCase。新增名称优先表达稳定对象、动作或轮廓，避免项目名、页面名、颜色名、尺寸名和版本尾缀。

`record.svg` 参考稿表达文档，不应使用容易与录制操作混淆的公共名Record；候选公共名可以是FileText。`close.svg` 应优先映射现有X，而不是新增一个同形Close；`settings.svg` 与 `check.svg` 应先审查现有Settings、Check。

这些映射是待审查提案，不是本轮新增导出。完整36枚映射见《基线审查》。已有Settings2、Maximize2、FileCode2等名称作为存量契约保留；新资产不继续用无说明数字后缀制造同义变体。

### 14.2 新增前的判定

先查是否已有相同语义；再确认现有字形是否能够在不误导的情况下复用；只有确实表达新对象或不同操作时才新增。不得因为喜欢另一种造型就建立同义图标。缺图时不得静默渲染空白或随便借用一个相近图标，必须记录缺口并给出清楚的文字降级。

### 14.3 每枚字形需要的记录

规格至少包括：稳定ID、候选／正式名称、中文语义、允许与禁止用途、所属家族、基准几何、最小尺寸、方向策略、归一化与微调记录、参考来源与许可记录、设计版本、批准状态、证据位置。

该记录是拟建立的设计元数据，不意味着当前 `Icon.tsx` 已读取这些字段。格式见《单枚图标规格模板》；实现时可以先使用Markdown记录，不为文档治理立即增加复杂运行时注册系统。

## 15. SVG 资产与安全边界

### 15.1 交付分层

原始可编辑稿、规范化SVG、React实现、导出PNG、参考板分别存放；不得把PNG当作生产图标源，也不通过自动描摹参考板生成最终路径。参考板负责说明设计，规范化SVG负责描述字形，React包装器负责宿主行为。

### 15.2 正式字形要求

必须保留统一viewBox、透明背景、可继承前景；可使用 `path`、`circle`、`ellipse`、`rect`、`line`、`polyline`、`polygon` 与必要的单层 `g`。复杂路径不是错误，但无意义的重复路径、隐藏对象与导出噪声必须移除。

禁止 `script`、事件属性、`foreignObject`、外部图片／URL引用、嵌入字体、任意样式表、滤镜、渐变和未经批准的mask／clipPath／use依赖。纯几何图标优先不产生全局ID，避免重复实例冲突。任何例外必须独立审查，不能因为SVG能显示就直接接入。

允许在源稿保留语义title；React组件的可访问名称按包装器契约处理，不能把固定中文title注入每个装饰实例。图标不直接接收网络下发的原始SVG字符串，不以 `dangerouslySetInnerHTML` 作为本体系的默认接入方式。

### 15.3 描边与导出优化

不要默认把描边转为填充轮廓；本系统以可维护的单色描边为基础。不要使用 `shape-rendering="crispEdges"` 强行改变曲线外观，也不要把 `non-scaling-stroke` 当优化选项自动添加。

优化器必须配置为保留viewBox、描边语义、必要的小数精度和方向；优化前后做同环境多尺寸比较。优化不应重写几何以“更接近网格”，也不得删除光学微调组。

单枚SVG应保持简洁；文本体积超过约4KiB时触发人工复审，但体积不是风格验收的替代指标。具体限制为项目维护门槛，不是浏览器硬限制。

## 16. React 集成与仓库结构

### 16.1 延续现有公共入口

本轮不另起一个平行图标框架。当前入口为 `@wzrhine/react` 与 `@wzrhine/react/icons`，后者导向 `packages/react/src/components/Icon.tsx`。后续新增优先在这个体系中完成，按需要整理内部文件，而不是立即拆新npm包。[^r-package]

当前实现通过 `name` 查询集中式PATHS。它提供稳定入口，但不能据此承诺“每次只打包使用的那一枚图标”；确有产物体积需求时，用真实打包测量决定是否增加静态逐图标入口，并经ADR处理。[^r-wrapper]

### 16.2 当前API不等于设计自由度

当前类型允许传入SVG属性，`strokeWidth`也可覆盖。这是已存在的API事实，并不意味着项目内可以为每一枚图标设置不同线宽。规范限制项目使用方式；未经迁移决策，不通过删除已发布属性来强制执行规范。

新能力如尺寸优化variant、显式decorative属性、自动RTL策略、基于元数据的校准、逐图标导出，均属于后续实现事项。本文件不宣称它们已经存在。

### 16.3 单一源与兼容边界

现行文档保留AgentIcon的16×16内部／兼容体系。新消费页面优先公共24u入口；不得为赶进度继续扩大临时16u旁路集合。既有AgentIcon和内联状态图标按组件逐批核对，不能整体替换viewBox后认为完成迁移。[^r-icon]

同一字形不得长期在展示站、组件源码、Agent包和业务项目各维护一份。若保留设计源SVG与React几何两种表示，必须明确一个生成方向并进行一致性检查；不能让两份都成为可独立编辑的正式源。

### 16.4 现行公共契约（继承自 Draft 0.1）

以下事实来自被替代的原 `ICONS.md`（Draft 0.1），仍然有效，并入本章保存：

- R01 采用库内原创 SVG 路线：`Icon` 可从 `@wzrhine/react` 或 `@wzrhine/react/icons` 导入。公共集合统一 24×24 viewBox、1.75 stroke、round cap/join、currentColor。`AgentIcon` 的 16×16 网格保留为已有内部/兼容图标体系；新消费界面优先使用公共入口。本仓不新增 lucide-react 运行时依赖。
- 三个图标组件（`Icon`、`AgentIcon`、`StatusGlyph`）的 `name` 均为开放集合（[ADR-0013](../development/adr/0013-open-taxonomies.md) §3）：内置名之外的取值必须同时传 `children`（自定义 SVG 内容，`data-icon`／`data-glyph` 携带自定义名）；对内置名传 `children` 则覆盖内置路径。这样宿主的产品图标可以进入任何接受图标的组件属性，而无需 fork 图标库。
- 展示站图标是 `apps/docs/src/icons.tsx` 中的原创 24×24 线性 SVG（1.75 stroke、round cap/join、`currentColor`）；组件内部的状态与控件图标是各组件源码内联的原创 SVG（多为 16×16 viewBox），默认 `aria-hidden`。提交任何新图标应附来源、语义定义、SVG 视口、截图与许可信息。

## 17. 从36枚参考草案到正式基线

### 17.1 冻结方向，不直接冻结参数

四张参考板用于保持整体语言，分别覆盖科研、档案、通用操作与光学落位。它们的共同方向可以被本规范继承；单枚细节、偏移、画布占用和小尺寸表现仍需逐枚审核。

尤其不能把参考板中的十字校准线、分格底板和橙色说明标记一起放进图标。静态界面示意不是已经完成的浏览器验收截图。

### 17.2 已知需要重点复核的草案

`play` 原有总平移与墨量重心统计并不支持直接宣布“已精确居中”；应拆开几何归一化与光学微调重新比较。`network`、`branch`、`download` 的重栅格化诊断触发拟定留白门槛，应先重审几何与边界。`download` 与 `upload` 的独立平移不同，需要成对验证托盘基线。复杂仪器则需特别看14／16px识别性。

这些结论来自参考包参数的复查，不是一次完整的浏览器视觉验收；详情、原始值和限制见《基线审查》。不得据此把其他草案默认标为通过。

### 17.3 先建立12枚基准候选

首批建议使用：Search、Folder、FileText、ArchiveCabinet、Settings、Check、X、Play、Layers、Scan、OpticalCore、Microscope。它们覆盖稀疏／密集、对称／非对称、圆／方、基础／研究等关键差异；名称除已存在项外均是候选名。

这12枚须先通过统一验收，才能成为后续扩展的“基准样本”。无人工批准之前统一标记为 `candidate`，不得仅因列入本节就叫黄金基线。后续每一批与其中适合的样本混排，而不是只和同批新图标相互比较。

## 18. 设计、实现与审批流程

**需求 → 复用判断 → 单枚规格 → 黑白母版 → 同族比较 → 光学校准 → 多尺寸与主题 → 真实组件 → 审批 → 发布基线。**

需求阶段明确用户实际要识别的对象或动作；初稿阶段先做黑白，不用颜色掩饰结构问题；校准阶段同时保存未校准和候选版本；集成阶段先确认布局责任，再修字形。

每批推荐6–12枚，优先按同一母体或相同使用场景组织；涉及公共几何、包装器或token的变更单独成批，不能与大规模图形新增混成无法评审的提交。

维护者负责设计采用与基线批准，实现者负责代码和证据，Agent可以绘制、检查和报告，但不得自动批准自己的风格例外。单人开发时可由维护者进行独立复看，保留作者自检与维护者确认两个记录，不能虚构第二名评审人。

## 19. 验收：自动检查与人工判断各负责什么

### 19.1 自动或程序化检查

适合自动化的事项：viewBox与基础属性、非法SVG节点与属性、名称唯一性、公共导出、路径有效性、明显越界、重复ID、实际DOM的可访问行为、包装器尺寸、指定环境截图差异，以及相同字形多表示的一致性。

bbox与墨量统计用于发现异常；没有统一算法能在本规范中替代所有光学校准判断。截图没有变化也不能证明旧基线没有缺陷。

### 19.2 人工检查

必须人工判定：语义是否清晰、家族是否一致、非对称形状是否看着居中、细节是否过密、状态切换是否跳位、同族比例是否协调、图形与文字关系是否自然。检查时既看无辅助线版本，也看校准线版本；既看原尺寸，也看放大结构。

### 19.3 最低证据矩阵

新增／重绘的每枚字形提供16／20／24px、浅／深主题的固定槽位对照；14／18px按声明或实际使用追加。受影响的按钮、导航、列表、输入框或工具栏提供真实运行截图；状态和RTL按语义适用，不为无方向图标制造无意义的镜像测试。

组件或布局一起改动时，遵守项目AGENTS的320／390／768／1280／1920视口要求；无需把每枚独立SVG机械乘上五种页面宽度，但必须证明其实际容器没有缩小、裁切或对齐失效。[^r-agents]

正式基线还需真实Windows/macOS目标环境抽样；仅完成部分环境时标记 `blocked` 或有范围的 `partial`，不能写全平台通过。本次文档交付没有执行这些产品测试。

### 19.4 阻断条件

语义错误、图标视觉明显偏移、非法资源、未说明的家族规则变化、缺少必要可访问名称、必要尺寸无法识别、未经批准覆盖基线、关键平台证据缺失，均不得以综合评分高为由放行。完整条目与记录格式见《验收清单》。

## 20. 防走形治理与变更控制

### 20.1 哪些变化必须上升为设计决策

改变viewBox、默认线宽、端点策略、线性／实心主风格、颜色职责、整个家族比例、公共命名策略或新增另一套运行时体系，必须提交ADR和代表性全族对照。单枚新图标不能顺带重新定义系统。

在既有规则内新增字形可走普通图标评审；对已发布字形的可见重绘，即便类型API不变，也必须记录视觉变更，提供前后对照与影响面，不可以“只是优化”跳过审核。

### 20.2 规范与字形分别版本化

规范维护 `specVersion`，单枚维护 `designRevision`，正式图像记录源文件hash与截图环境。版本号只证明记录身份，不自动证明质量。状态建议使用 `draft → candidate → approved → deprecated`，其中approved仍要注明已验证尺寸与平台范围；公开发布另记录发布版本。

### 20.3 不允许静默刷新截图

截图变化时先解释差异，再确认修复或接受；禁止为了让测试变绿直接更新所有基线。自动化脚本不能自行提升草案状态、选择视觉例外或把旧图标替换成模型新生成的风格。

### 20.4 单枚例外不传播

例外必须记录受影响字形、具体规则、必要性、替代方案、批准人、适用尺寸／场景和复审触发条件。一个卫星图标需要特殊角度，不意味着所有档案图标都可以倾斜；一个复杂研究图标最小20px，也不意味着全库放弃16px。

### 20.5 审查节奏

每新增一批，将其与正式基准混排；每个版本发布前抽查全部图标的缩略总览、大小差异、颜色状态和语义重复。发现走形回到母体与规则修正，不靠给所有旧图标同步加装饰“追平”。

## 21. 来源、许可与交付记录

保存来源声明、作者／生成方式、原始输入、设计修改记录和许可检查结果。项目气质可以受科研与档案视觉启发，但不得把游戏原图抠图、描摹或改色后标为原创。已有源码的来源声明不替代逐项许可复核。

参考包中PNG和SVG均作为探索材料；本次文档附带的四张参考板保持原内容，保留候选身份。不要将字体文件、无来源图像或未经授权的商标并入图标包。

每次图标交付至少包括：规范化矢量、单枚规格、原尺寸与主题证据、组件落位证据、来源记录、变更说明、验收结论。仅有一张漂亮九宫格不是正式交付。

## 23. 每次新增图标前的十条自检

1. 我能用一句话说清楚它的语义，以及不能代表什么吗？
2. 现有公共集合是否已有等价图标？
3. 它沿用了哪一枚正式母体或基准样本？
4. 去掉颜色、背景和文字后，它仍属于这个家族吗？
5. 每个细节是否必要，描边后是否仍有清楚间隙？
6. 我处理的是字形光学位置，还是其实该修容器？
7. 16px是否能看清；实际使用的14／18px是否另有证据？
8. 深色、选中、禁用和必要的RTL语义是否正确？
9. 这次是否绕过公共入口、增加私有副本或修改全局规则？
10. 结论是否由真实证据支持，而不是来自参考图、算法分数或“应该没问题”？

**本规范最终要保证的不是所有图标长得一样，而是不同图标在语义、几何、视觉重心和使用行为上遵循同一套可持续维护的规则。**
