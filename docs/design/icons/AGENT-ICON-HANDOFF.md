# Icon开发 Agent 工作约束与交接提示词

版本：1.0 提案版｜这是一份任务交接文档，不是已安装的新Skill，也不代表已修改仓库AGENTS。

## 一、可复制的任务开场

你正在为 `BaiZhi967/WzRhineLab-UI` 开发或维护原创图标。你的目标是延续项目既有的科研机构／档案语言，保证语义、小尺寸识别、视觉居中与家族一致性，而不是为每个任务重新设计一套风格。

首先读取仓库AGENTS.md、DESIGN.md、docs/design/ICONS.md，以及本次涉及的STYLE、MOTION、ACCESSIBILITY文档。若本套规范尚未进入仓库，先明确它来自本轮交付包并确认任务采用版本，不得声称仓库已经存在这些路径。读取当前公共Icon实现与包导出，查清真实IconName和token，不能只照文档或记忆推断API。

本次开始前需要明确：处理哪些图标，新增还是替换，真实消费场景，支持尺寸，是否授权修改代码／提交／推送，以及哪些平台可以实际验证。没有授权的外部写入或发布不执行。

## 二、不可改变的设计底线

使用24u母版、默认1.75u描边、round cap与round join、单色currentColor、透明字形。维持同族圆环、折角、支架、页签和内部间距；通用操作不加多余科研装饰。不得混入外部图标库、字体图标、emoji、3D、渐变、发光、厚重实心轮廓或业务私有变体。

主规范的数字门槛是已采用版本的项目规则，不是任意选择的参考。遇到确有必要的例外，记录问题与方案交维护者决定，不自行修改规则使当前图形“通过”。

颜色从宿主token继承。不要把研究橙硬编码进图形，不用白色图块遮挡交叉，不为深色主题加粗，不在hover时切换另一套重量。当前icon-size token包含14／16／20px，不得因参考板有16／20／24px而偷偷修改公共token。

## 三、居中处理必须遵守的流程

先判断问题来自槽位、源稿几何还是字形感知。源稿归一化和光学微调分别记录；旧参考包中的总translation不是统一规则，也不保证光学正确。

对非对称字形输出零微调和邻近候选，在16／20／24px固定槽位、浅／深主题和真实组件中比较。bbox与墨量重心只做诊断。只在库内几何或一次平移组中保存补偿，禁止在消费页面散落margin、top、translate等修补。

成对图标必须一起看：上传／下载托盘，运行／暂停的位置，展开／收起的旋转中心。辅助线版本和无辅助线版本都要检查，不能只看放大截图。

## 四、工程边界

优先复用现有 `@wzrhine/react/icons` 公共入口，不在业务项目或文档站另建长期图库。添加前查现有名称，尤其注意Settings、Check、X等已有语义。参考稿kebab-case文件名不等于当前IconName。

当前API允许的属性不代表可以随意改变风格；也不得未经迁移决策删除已发布属性。尺寸自动变体、decorative新属性、RTL自动镜像、逐图标导出和元数据registry如尚未实现，不得写出假装已经可用的示例。

修改既有AgentIcon或内联图标时按组件逐批验证，不以全局替换viewBox、全局CSS补偿或复制同名图形解决。SVG必须通过结构与资源检查；不得加入任意外部内容或使用动态原始SVG注入绕过公共体系。

## 五、输出和证据

每枚新增／重绘图标提供规格记录、矢量／实现差异、校准说明、支持尺寸、主题与组件证据。汇报要区分“本轮实际做了什么”“实际检查了什么”“未执行什么”“需要维护者决定什么”。

只有实际执行成功的命令才能写通过；只有维护者真实确认后才能写批准。Linux、仿真浏览器或静态参考图不能冒充Windows／macOS实际运行证据。没有目标平台时保留阻塞项，不自填结果。

更新截图前说明变化，不为让测试变绿自动刷新全部基线。不得自动批准自己的风格例外，不把所有36枚参考稿直接提升为正式资产。

遵从仓库关于分支、提交和GitHub Actions配额的规定；不因为要做图标验收就擅自新增workflow。提交信息延续项目中文习惯。
