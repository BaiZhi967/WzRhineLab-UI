# 真实需求插入与 Agent 引导流程

本文件规定：当其他项目在实际使用 WzRhineLab-UI 时发现缺少组件，如何让 Agent 按顺序收集信息、判断组件归属、确定最小支持范围、插入当前路线，并在交付后回填主线。

它补充以下规划文件：

- [长期路线图](roadmap.md)
- [组件平台长期规划](component-platform-plan.md)
- [执行清单](execution-backlog.md)
- [组件需求记录模板](templates/component-demand.md)

## 1. 核心原则

WzRhineLab-UI 的 M8–M18 是默认能力演进顺序。真实项目可以改变“先做哪个组件”，但不能随意改变：

- 组件应该放在哪一层；
- 组件依赖哪个行为和渲染基座；
- API、可访问性、动效、响应式和 SSR 标准；
- 组件库和消费项目各自的验收范围；
- 插入任务完成后如何回填路线和恢复主线。

“不影响整体路线”具体表示：

1. 不绕过既有架构边界；
2. 不因为单个需求引入第二套 headless 行为底座；
3. 不把展示效果和业务结果绑定；
4. 不把局部组件完成误记为整个里程碑完成；
5. 不让插入任务无限扩张；
6. 始终记录插入前的主线位置、恢复位置和未完成范围。

插入任务会占用开发精力，因此它可能改变实际优先级。路线稳定性通过依赖、范围、质量和记录保持，而不是通过禁止调整顺序保持。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 主线 | M8–M18 的默认里程碑顺序 |
| 插入需求 | 来自真实消费项目、会阻塞实际开发的组件或能力请求 |
| 消费项目 | 使用 WzRhineLab-UI 的其他应用或页面项目 |
| 组件归属 | 判断需求属于基础组件、Rhine 领域模式、消费项目组合还是独立效果适配器 |
| 最小支持闭环 | 足以让当前消费场景真实运行，同时不扩张为整个未来里程碑的范围 |
| 依赖闭包 | 本次组件必须具备的行为、语义、token、动效、渲染和测试依赖 |
| 消费项目验收 | 在真实应用中安装、导入、运行、构建并验证组件 |
| 路线回填 | 将提前交付结果记录回原目标里程碑，并删除重复待办 |
| 恢复点 | 插入需求完成后，主线继续推进的明确任务位置 |

## 3. 什么时候可以插入主线

以下条件同时满足时，可以把需求放入插入队列：

- 当前消费项目确实被缺少的能力阻塞；
- 已经有明确页面、用户操作或数据场景；
- 可以描述一个有限的最小支持范围；
- 组件归属和边界可以说明；
- 必要依赖不会破坏现有 package 边界；
- 组件的库内验收和消费项目验收可以执行。

一个消费项目就可以提出插入需求。“至少两个项目复用”是复用价值评分项，不是阻塞型需求的硬门槛。

只有概念图、竞品存在但没有使用场景、或者只是希望“以后可能用到”的组件，先放入候选或 showcase backlog，不打断当前主线。

## 4. Agent 必须按顺序引导补充信息

用户提出“需要支持某个组件”时，Agent 不应立即写代码，也不应一次性抛出一长串问题。Agent 应按下列顺序逐步提问，一次只问一个最影响判断的问题。

### 阶段 A：确认真实场景

1. 这个组件出现在哪个项目、页面和用户流程中？
2. 用户会对它执行什么操作？
3. 当前页面使用了什么临时实现或替代组件？
4. 当前替代方案具体阻塞了什么：行为、键盘、可访问性、视觉一致性、性能还是开发效率？

阶段 A 的目标是确认这是实际需求，而不是抽象的组件愿望。

### 阶段 B：确定最小行为

5. 当前场景必须支持哪些状态？
6. 哪些状态可以暂时延后？
7. 数据是静态的、受控的、异步的，还是由消费项目自行请求？
8. 组件需要单选、多选、范围选择、拖拽、搜索、虚拟化或其他高级能力吗？

Agent 应把用户回答转换成“本次支持”和“本次延后”两张清单。

### 阶段 C：判断组件归属

9. 这是可以被多个应用复用的通用行为吗？
10. 它是否绑定账号、权限、后端接口、文件系统或特定业务实体？
11. 它能否由现有基础组件在消费项目中组合完成？
12. 它更接近基础组件、Rhine 领域模式、业务页面组合还是 Effects 适配器？

如果需求深度绑定业务模型，Agent 应优先建议留在消费项目；可以把其中通用的子组件提取回库，但不能把完整业务模块直接塞进基础包。

### 阶段 D：确认依赖和 API

13. 是否可以使用现有 Base UI 1.9.0、tokens 和 `motion/react`？
14. 是否需要新增依赖、package、渲染内核或行为底座？
15. 需要受控、非受控还是两者都支持？
16. 需要哪些 slots、children、render props、ref 或原生 DOM props？
17. 是否存在 SSR、hydration、宿主样式污染或跨项目 CSS 风险？

如果需求引入第二套 headless 底座、Canvas/WebGL、公共 package 边界变化或新的状态管理方式，Agent 必须先升级为架构评估，不得把它伪装成普通组件插入。

### 阶段 E：确认交互、无障碍和动效

18. 键盘如何操作？
19. focus 如何进入、移动、离开和恢复？
20. 屏幕阅读器需要读出哪些名称、角色、状态和异步变化？
21. loading、empty、error、disabled 和 invalid 如何表达？
22. 动效表达什么，能否中断，reduced motion 时如何降级？
23. 在窄屏、宽屏、长中文和英文长词下如何布局？

### 阶段 F：确认验收和路线影响

24. 消费项目中哪个真实页面用于接入验收？
25. 什么结果出现后，才算解决这次阻塞？
26. 组件库需要哪些单测、E2E、axe、视觉和手工验收？
27. 当前主线推进到哪个任务？
28. 插入完成后从哪个任务恢复？
29. 哪些未来能力明确不在本次范围内？

Agent 在得到足够信息后，应先回写一份“需求范围卡”，让用户确认范围，再进入实现。范围卡需要包含：

- 场景和阻塞；
- 组件归属；
- 目标里程碑；
- 本次支持；
- 本次延后；
- 依赖闭包；
- 库内验收；
- 消费项目验收；
- 主线暂停点；
- 主线恢复点；
- 路线回填位置。

## 5. 归属决策

| 需求类型 | 识别方式 | 默认位置 |
| --- | --- | --- |
| 基础组件 | 通用语义和交互，多项目可复用 | `@wzrhine/react` |
| Rhine 领域模式 | 面向科研、档案、实验、Agent、证据链场景 | Rhine Patterns 或独立模式包 |
| 业务页面模块 | 绑定账号、接口、权限、文件系统或业务实体 | 消费项目 |
| 页面组合 | 已有组件可以组合解决 | 消费项目 |
| 展示型效果 | 粒子、噪声、3D、复杂渲染或大规模视觉效果 | `@wzrhine/effects/*` 或独立适配器 |

例如，通用 Tree 可以进入组件库；绑定本地文件系统、权限和业务数据的资源管理器留在消费项目。通用 Card、Badge、Menu 可以进入组件库；绑定内容发布状态的完整 Kanban 留在消费项目或未来领域模式中。

## 6. 插入任务的最小支持闭环

插入任务应围绕当前真实场景建立最小闭环：

1. 明确组件 API 和状态矩阵；
2. 使用现有行为、token 和动效基座；
3. 实现当前场景真正使用的行为；
4. 补齐当前范围内的键盘和屏幕阅读器语义；
5. 补齐 loading、empty、error 和 reduced motion；
6. 写组件文档和消费示例；
7. 完成组件库验收；
8. 安装或链接到消费项目；
9. 完成消费项目真实页面验收；
10. 记录限制、后续增强和路线回填。

不应在同一个插入任务中顺手完成整个未来里程碑。例如项目只需要 Tree 的展开、选中和键盘导航时，不应自动扩展为虚拟化、拖拽、右键菜单、树形表格和文件系统适配器。

## 7. 两层验收

### 7.1 组件库验收

根据组件影响选择并真实执行：

- TypeScript 和公开 Props；
- 单元测试；
- 受控 / 非受控；
- 键盘和 focus；
- axe；
- Chromium、Firefox、WebKit；
- 视觉基线；
- reduced motion；
- SSR / hydration；
- CSS 隔离；
- API report；
- 包构建和 tree-shaking。

### 7.2 消费项目验收

至少验证：

- 组件可以被消费项目安装或链接；
- 导入路径、类型和样式正确；
- 宿主项目的全局样式不会破坏组件；
- 真实数据、异步状态和业务事件可以接入；
- 页面在目标布局和数据密度下可用；
- 消费项目的构建、SSR 或桌面运行正常；
- 当前组件确实替代了原来的临时实现；
- 限制和未支持能力已经记录。

组件库测试通过但消费项目未接入时，状态最多是“库内完成，等待消费验证”，不能写成“已经解决项目需求”。

## 8. 路线状态与回填

插入需求使用以下状态：

| 状态 | 含义 |
| --- | --- |
| Requested | 已提出，尚未完成分流 |
| Scoped | 已确认场景、归属、范围和依赖 |
| Implementing | 正在实现，主线有明确暂停点 |
| Consumer validating | 库内通过，正在消费项目验证 |
| Promoted | 已回填目标里程碑并完成记录 |
| Deferred | 有意延后，原因已记录 |
| Rejected | 不进入组件库或当前路线 |

每个插入需求都要记录：

```text
插入前主线：
插入目标里程碑：
插入原因：
允许修改：
明确禁止扩张：
组件库验收：
消费项目验收：
主线恢复点：
路线回填位置：
```

提前完成的组件应在原目标里程碑中标记为“提前交付”，同时保留该里程碑其他待办。组件完成不等于里程碑完成。

如果连续出现多个插入需求，Agent 应停止继续接收新的插入实现，先输出一次主线重排建议，列出：

- 当前主线；
- 已完成的提前组件；
- 尚未完成的插入需求；
- 被推迟的主线任务；
- 需要保留的架构依赖；
- 建议的恢复顺序。

## 10. Tree 插入示例

当当前主线正在 M8，而消费项目需要 Tree 时：

本次可以支持：

- Tree / TreeItem；
- 展开和折叠；
- 受控 / 非受控展开状态；
- 单选；
- 键盘方向键；
- 基础异步 loading；
- empty / error；
- 基础动效和 reduced motion；
- 组件库与消费项目验收。

本次明确延后：

- 虚拟化；
- 拖拽排序；
- 多选和范围选择；
- 节点搜索；
- 右键菜单；
- 树形表格；
- 文件系统适配器。

路线记录为：

```text
M8：继续进行
M12：Tree 已提前交付
M12：其他 Advanced interaction 仍待完成
```

Tree 完成后，主线恢复到插入前记录的 M8 任务；未来进入 M12 时，根据新的真实场景决定是否增加 Tree 的增强能力。

## 11. 维护要求

- 需求记录使用 [组件需求记录模板](templates/component-demand.md)；
- 一次只处理一个插入需求，避免多个需求并行打散主线；
- 插入任务必须有明确的消费项目和真实页面；
- 所有“已支持”“已解决”“可发布”都必须链接到实际验收证据；
- 不使用具体时间安排替代顺序和依赖；
- 不把实验性 API 默认加入稳定公共导出；
- 不把 Canvas/WebGL 或大型效果依赖加入基础组件依赖链；
- 插入任务完成后同步更新路线回填、执行清单和组件文档。
